# Experiments building Haskell with Buck2

This repository contains some experiments with the Buck2 build system. I am
interested in how it can be used to build Haskell projects that use cabal.

There are three approaches side by side:

- `BUCK` and `tmp/alex-3.5.1.0/BUCK` use the Haskell rules from buck2's
  prelude, through a small wrapper (`rules/haskell/defs.bzl`) that lets a
  target name the packages that come with the compiler.
- In `projects/` I map a build plan generated by cabal-install into a buck2
  target graph. This relies on Setup.hs for building packages just like
  cabal-install does. The rules are in `rules/haskell/cabal_install`. At the
  moment only `projects/shake` has a plan made with the current GHC.
- In `examples/` I transcribe `.cabal` files stanza by stanza into targets that
  do what Cabal does for `build-type: Simple`, without Setup.hs. The rules are
  in `rules/haskell/cabal`. `examples/prelude` is a library and an executable
  built by the rules of the prelude on top of one of these libraries.

Not everything works at the moment and I keep reworking the code significantly.

## Instructions for testing

GHC 9.12.2 and cabal-install 3.14.2.0 are downloaded by buck2, using GHCup's
metadata. The tools I use (buck2 itself, buildifier, lefthook) can be installed
with [mise](https://mise.jdx.dev):

```bash
$ mise install
```

You also need:

- a C compiler and a linker, since buck2 uses the ones on your system;
- `curl`, `jq` and a Hackage index downloaded with `cabal update`, only to
  make a build plan (e.g. `buck2 build //projects/shake:plan`).

Now you can try to build things, e.g.

```bash
$ buck2 run //:main
$ buck2 run //examples/hello:exe
$ buck2 run $(buck2 targets //projects/shake: | grep -- '-e-shake-') -- --version
```

The last one builds shake and everything it depends on. Each unit of the build
plan is a target named after its unit-id, `buck2 targets //projects/shake:`
lists them.

Everything is built with a GHC that buck2 downloads. To use the `ghc` in path
instead pass `--config haskell.toolchain=toolchains//:ghc`; the build plan of
shake is made for the downloaded one and will not build.

# Notes and rants

## `-package` vs `-package-id`

I keep fighting with the haskell rules in the prelude. I believe they are too
opinionated and do not support more general use cases. In particular BUCK should
not use `-package` to pass dependencies to GHC since this will leave GHC to
figure out which unit to pick for a given package name. The build-system should
be extremely precise in the instructions it gives to the compiler.
The dependencies in both the global packagedb and cabal-install build plans are
indeed expressed in terms of unit-id.

For a while I used a fork of the prelude, customised to use `-package-id` in
place of `-package`. Now I am back on the prelude that comes with buck2 and the
situation is mixed. The rules in `rules/haskell/cabal_install` and
`rules/haskell/cabal` always name a dependency by its unit-id. The targets
written by hand still name the packages that come with the compiler by package
name (see `toolchain_libs` and `haskell_unit` in `rules/haskell/defs.bzl`).
